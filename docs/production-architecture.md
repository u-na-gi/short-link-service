## 運用の前提条件 (単一プロセス制約)

### インメモリ保持による制約

本サービスは要件に基づき、短縮リンクの対応データをすべてサーバ内の**インメモリ (`TrieMap`) で保持**しています。外部データベースへの永続化は行っていません。

この設計に伴い、以下の運用上の制約が存在します。

1. **単一プロセスでの稼働が必須**:
   - 複数台のインスタンスで負荷分散（ALB によるラウンドロビン等）を行うと、インスタンス A で生成した短縮 URL がインスタンス B では未登録（404 Not Found）となったり、同一元 URL に対してインスタンスごとに異なる短縮コードが発行されたりします。
   - そのため、**常に 1 プロセス（単一インスタンス・単一コンテナ）で稼働させる必要があります**。
2. **プロセス再起動によるデータ消失**:
   - サーバプロセスの再起動やコンテナの再デプロイを行うと、それまでに発行された短縮リンクデータはすべて消失します。

### 将来のスケールアウト方針

本サービスを複数台構成にスケールアウト、あるいは耐障害性を向上させる場合は、リポジトリ層を外部の共有データストアに差し替える必要があります。

- ドメイン層のインターフェース `domain.ShortLinkRepository` はインフラ詳細から独立しているため、このインターフェースを実装した永続化クラス（例: Amazon DynamoDB、Redis、Amazon Aurora 等）を新規作成し、`Module.scala` の Guice バインディングを差し替えることで、上位のユースケースやコントローラーを変更することなくスケールアウトが可能になります。

## 本番アーキテクチャ構想 (CloudFront + ECS on EC2)

現行のインメモリ仕様を満たしつつ、AWS 上で高可用かつセキュアにサービスを公開する場合のインフラ設計構想です（※Terraform 等による実装は今後の TODO）。

### インフラ構成図

```mermaid
flowchart TD
    User["利用者 / ブラウザ"]
    CF["Amazon CloudFront\n(https://example.com)"]
    S3["Amazon S3 バケット\n(フロントエンド成果物 dist/)"]
    EC2["ECS on EC2 (1台・単一タスク)\nPlay Framework (:9000)"]

    User -->|HTTPS| CF
    CF -->|Default (*) ビヘイビア\nS3 OAC 経由| S3
    CF -->|/api/* および /????????\nキャッシュ無効| EC2
```

### 構成要素と責務

1. **Amazon CloudFront**:
   - 単一の公開ドメイン (`https://example.com`) で TLS 終端を行います。
   - パスパターンに基づいてフロントエンドの静的アセットとバックエンド API を同一オリジンとしてルーティングします。
2. **Amazon S3 (フロントエンド配信)**:
   - `src/front` で `bun run build` して生成された静的ファイル群 (`dist/`) を配置します。
   - CloudFront の Origin Access Control (OAC) を使用して S3 バケット自体はパブリック非公開とします。
   - Default (*) ビヘイビアとしてキャッシュ付きで高速配信します。
3. **ECS on EC2 (バックエンド API)**:
   - Play Framework の API サーバをコンテナとして実行します。
   - `/api/*` および `^/[A-Za-z0-9]{8}$` のパスパターンを EC2 へ転送します（API 応答やリダイレクトはキャッシュ無効化）。

### ECS on EC2 (単一タスク) の運用設計

インメモリ整合性を維持するため、ECS のサービス定義およびタスク配置は以下のように設計します。

- **ALB なしのプライベート配置**:
  - 不必要なロードバランサーを排し、CloudFront の VPC Origin を用いてプライベートサブネット内の EC2 へ直接トラフィックを流します。
- **タスク数とローリングアップデート設定**:
  - `desiredCount = 1`
  - `maximumPercent = 100`
  - `minimumHealthyPercent = 0`
  - デプロイ時であっても新旧コンテナが同時に並行稼働することを防ぎ、常に厳密な単一インスタンスを保ちます。
- **EC2 を採用する理由**:
  - AWS Fargate ではタスク停止・起動のたびにプライベート IP が変動し、ALB を挟まない構成での CloudFront VPC Origin 連携が困難であるため、固定 IP または単一ホストで管理可能な EC2 起動タイプを採用します。

### 本番運用時に必要な設定

本番環境にデプロイする際、以下の環境変数および Play Framework 設定を注入する必要があります。

- `SHORTENER_BASE_URL`: 本番公開ドメイン（`https://example.com`）を指定。
- `play.http.secret.key`: セッション暗号化やアプリケーション署名用のシークレットキー（本番用の安全なランダム文字列を設定）。
- `play.filters.hosts.allowed`: CloudFront 経由でアクセスされるドメイン（`example.com` など）を許可リストに追加。
